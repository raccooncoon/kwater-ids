선택지 ① — 진정한 통합포털
단일 로그인·로그아웃, 통합 권한, 일관된 사용자 경험. 포털 간 세션과 권한이 연결된 하나의 시스템.
🗂️
선택지 ② — 독립 포털의 모음
각자 독립적으로 동작하는 별도 서비스들. 통합포털은 메뉴·링크·대시보드 역할만 수행.
현재 제안의 위치: 둘 중 어느 쪽인지 명확하지 않은 상태에서 양쪽의 단점만 결합한 구조로 가고 있습니다.
용어 정의
IdP와 IDS의 차이
비슷해 보이지만 역할이 다릅니다. 이 차이가 이번 결정의 핵심입니다.
IdP — Identity Provider
표준 용어
"이 사용자가 누구인가"를 증명하는 인증 주체.
OIDC/SAML 프로토콜로 ID Token·Access Token 발급.
예: Google, Microsoft Entra ID, Okta, Keycloak, K-water 오아시스
IDS — Identity Server
사내 통합인증 서버
조직 내부에 두는 자체 인증 서버. 외부 IdP를 페더레이션하면서 SSO 운영에 필요한 추가 기능 제공.
주요 역할:
• 외부 IdP(오아시스) 페더레이션
• 각 포털용 audience로 토큰 재발급 (Token Exchange)
• 세션 중앙 관리 + 로그아웃 전파 (SLO)
• 통합 권한(RBAC) 관리
• 감사 로그 통합 수집
관계: IDS는 일종의 자체 IdP이면서, 외부 IdP(오아시스)와 하위 포털 사이의 중간 계층 역할.

이번 프로젝트:
• 오아시스 = K-water가 제공하는 외부 IdP (고정)
• IDS = 통합포털 사업에서 별도 구축 검토 중인 인증 서버
• A안 = 오아시스 + IDS / C안 = 오아시스만, IDS 없음

핵심: A와 B는 각각 명확한 트레이드오프가 있습니다. C는 트레이드오프 없이 단점만 모은 구조입니다.

C안의 기술적 결과 ①
토큰을 하위 포털에
어떻게 전달할 것인가?
통합포털 구조를 유지하면서 IDS를 빼면, 통합포털이 받은 토큰을 하위 포털에 직접 전달해야 합니다. 가능한 방식과 위험:
① URL Query String 금지
cmp.kwater.or.kr/?access_token=eyJhbGc...
브라우저 히스토리·서버 로그·Referer 누출. RFC 6819 명시적 금지.
② Cookie Domain 공유 위험
한 포털 XSS = 전 포털 토큰 동시 탈취. 가장 약한 포털이 전체 보안 수준 결정.
③ PostMessage 실수↑
origin 검증 한 줄만 빠져도 임의 사이트로 토큰 유출. JS 메모리 노출 → XSS 표면 확대.
④ Form POST Redirect 비표준
매 페이지 전환마다 재전송, MITM 시 본문 노출. OIDC 표준 아님.
⑤ Backend Session Bridge 유일 권장
백엔드끼리 토큰 교환, 브라우저엔 세션 ID만. → 결국 이게 IDS 그 자체.
역설: 안전한 토큰 전달 방식 = IDS를 만드는 것. C안에서 안전한 방식을 선택하려면 결국 A안이 됩니다.
C안의 기술적 결과 ②
Audience 불일치
— 토큰 검증의 한계
외부 IdP가 발급한 토큰의 aud 클레임은 해당 IdP용입니다. 하위 포털이 이를 그대로 검증·사용할 수 없습니다.
{ "iss": "https://oasis.kwater.or.kr", "aud": "oasis-resource-server", ← 외부 IdP용 "sub": "user123", "exp": 1734567890 }
① 표준 검증 실패
하위 포털이 자신의 audience를 기대하지만 토큰엔 외부 IdP가 적혀 있음. RFC 7519 표준 검증 실패.
② Audience 검증 생략 → 재사용 공격
편의상 aud 검증을 우회하면, 한 포털에서 탈취된 토큰을 모든 포털에서 그대로 사용 가능한 구조가 됩니다.
③ Introspection 호출 부하 집중
매 요청마다 외부 IdP에 검증 요청 → 외부 의존도 극대화·SPOF 형성.
정상 설계: IDS가 외부 토큰을 받아 각 포털용 audience로 재서명한 새 토큰 발급 (OIDC Token Exchange — RFC 8693). C안에서는 이 계층이 없어 해결 불가.
C안의 기술적 결과 ③
토큰 만료·갱신
흐름이 C안에 없다
C안은 토큰 발급·전달만 다룰 뿐, "만료되면 누가 어떻게 갱신하는가"가 설계에서 빠져 있습니다. 가능한 시나리오는 모두 문제가 있습니다.
시나리오 ① 하위 시스템이 직접 OASIS에 refresh 최악
Refresh Token이 모든 시스템(외부 회사 포함)에 퍼짐. Refresh Token은 Access Token보다 훨씬 강력 — 새 토큰 무한 발급 가능. 한 외부 회사에서 유출되면 그 사용자 계정을 영구적으로 장악할 수 있음.
시나리오 ② 만료 시 재로그인 강요 UX 파괴
하위 시스템이 401 받으면 사용자에게 OASIS 재로그인 요구. 5~15분마다 로그인 팝업 → SSO 도입 의미 상실.
시나리오 ③ 메인 포털이 토큰 공유 파급 ↑
메인 포털이 refresh해서 새 토큰을 하위에 또 뿌림 → 슬라이드 5의 토큰 전달 방식 문제가 매번 반복. 갱신 주기마다 노출 표면 증가.
✅ 정상 설계 — 메인 포털 단독 보유 권장
Refresh Token은 메인 포털(또는 IDS)만 보유. 하위 시스템은 401 받으면 브로커에 재요청 → 브로커가 새 short-lived 토큰을 발급해 전달. Refresh Token은 절대 외부 경계를 넘지 않음.
핵심: 토큰 수명 관리는 SSO 설계의 절반입니다. C안에 갱신 흐름이 빠져 있다는 건 운영 단계에 폭탄을 남기는 것과 같습니다.
C안의 기술적 결과 ④
외부 회사 경계 +
JWT 폐기 불가
C안에서는 OASIS 원본 토큰이 외부 3개사 시스템에 그대로 상주합니다. 신뢰 도메인 경계 자체가 흐려집니다.
① 한 회사 유출 = OASIS 전체 노출
하위 시스템·솔루션 UI가 외부 회사 것이라면, 그 회사 인프라에 OASIS 원본 토큰이 상주.
한 회사에서 유출되면 OASIS 신뢰 도메인 전체가 동시에 노출. 토큰 폐기·감사 통제권을 K-water가 잃습니다.

※ 같은 회사인 CMP는 절충 가능. 외부 회사엔 적용 불가.
② JWT라 만료 전 강제 폐기 불가
OASIS 토큰은 JWT (자체 검증 구조). 서버 조회 없이 서명만으로 유효성 판정 → 발급 후 서버가 "이 토큰 폐기"를 강제할 방법이 없음.

결과: • 사용자가 메인에서 로그아웃해도 → 하위 시스템엔 exp까지 그대로 유효
• 토큰 탈취 발견해도 → 만료 시점까지 차단 불가
• 공용 PC·실수 노출 시 대응 수단 부재
③ Single Logout (SLO) 작동 불가
C안 자체가 "하위 시스템에서 로그아웃 동기화 불가"를 한계로 인정하고 있음.

SSO를 도입하면서 SLO를 포기하는 것 — 로그아웃의 책임을 사용자에게 떠넘기는 설계. ISMS-P 2.10.4 (세션 관리) 위반.
정상 설계: 외부 시스템엔 메인 포털(브로커)이 재발급한 회사별 audience·최소 scope·short-lived 토큰만 전달. OASIS 원본은 경계를 넘지 않음. 폐기는 short-lived(5~15분) + jti blocklist로 상쇄.
C안 운영 시나리오 ①
퇴직자/계정 비활성화
→ 즉시 차단 불가
C안에는 세션 중앙 제어 계층이 없습니다. 외부 IdP에서 계정을 차단해도 각 포털의 토큰은 독립적으로 살아있습니다.

②

③

④
결과 — 내부 시스템 무단 접근 퇴직자 또는 탈취 계정이 최대 1시간 동안 내부 시스템 접근 가능.
원인: C안에는 IDS가 없어 Back-Channel Logout·토큰 일괄 무효화 불가. A안이라면 IDS가 즉시 모든 포털에 차단 전파.

2.5.1
접근권한 즉시 회수

ISMS-P: 인사이동·퇴직 시 접근권한을 즉시 회수해야 함.
C안에서는 "즉시"가 아니라 "토큰 만료 시" 회수 → 감사 지적 대상.

2.10.4
세션 관리 및 타임아웃

단일 로그아웃 후 모든 연계 시스템에서 세션 종료해야 함.
C안의 독립 세션 관리는 이 요건 충족 불가.

2.9.1
접근 로그 중앙 수집

사용자 시스템 접근 이력을 단일 감사 로그로 관리해야 함.
C안의 포털별 분산 로그는 상관분석·침해 추적 불가.

2.5.2
권한 최소화 원칙

역할 변경 시 연계 시스템 전체에 즉시 반영 필요.
포털별 독립 권한 DB는 정합성 보장 불가.

시스템 성격별로
설계를 쪼개면 풀린다

① 내부 시스템 (CMP, 같은 회사)
OASIS JWT 패스스루 유지 + JWKS 자체 검증.
같은 신뢰 도메인 안이라 토큰이 경계를 넘지 않음.
→ 저공수로 운영 가능.
② 외부 3개사 시스템
메인 포털이 내부 JWT 재발급 브로커 역할.
OASIS 원본 토큰은 외부 경계를 넘지 않음.
회사별 aud + 최소 scope + short-lived 토큰만 발급.
→ 문제 ① (외부 경계) · ③ (aud 약화) 해소.
③ 로그아웃·폐기 (문제 ②)
• 토큰 수명을 5~15분 short-lived로 단축 → JWT 폐기 불가를 시간으로 상쇄
• 메인 포털 세션 무효화로 갱신 차단 (브로커가 거부)
• 완전한 SLO 필요 시 jti blocklist 도입
→ 공용 PC·탈취 대응 수단 확보.
④ 만료·갱신 (문제 ④)
• Refresh Token은 메인 포털만 보유. 외부 회사에 절대 전달 안 함.
• 하위 시스템은 401 받으면 메인 포털(브로커)에 새 토큰 재요청.
→ Refresh Token 확산 위험 차단.
구분토큰 처리관리 주체
내부 (CMP)OASIS JWT 직접 검증각 시스템 (JWKS)
외부 3개사재발급된 short-lived JWT메인 포털 브로커
Refresh Token외부로 전달 안 함메인 포털 단독
로그아웃·폐기short-lived + jti blocklist메인 포털 세션
정리: 같은 "C안"이라도 내부엔 패스스루, 외부엔 브로커 재발급. 시스템 신뢰 경계를 기준으로 설계가 갈려야 토큰 패스스루의 위험이 외부로 새지 않습니다.

부록 ① 권한 관리
권한 관리는
어디서 해야 하는가?
인증(Authentication)과 권한(Authorization)은 분리되어 다뤄야 합니다. 한 곳에서 다 하려고 하면 둘 다 망가집니다.
권한은 두 층으로 나뉩니다
구분예시관리 위치
거친 권한
Coarse-grained		 역할(관리자/일반/외부)
포털 접근 가능 여부		 IDS
중앙 집중

자체 관리
IDS가 책임지는 것
• 사용자–역할 매핑 (RBAC)
• 부서·그룹 정보 (오아시스에서 동기화)
• 역할 변경 시 모든 포털 토큰 무효화
• 권한 변경 이력 감사 로그
각 포털이 책임지는 것
• 리소스 단위 ACL
  (CMP 워크로드, 데이터허브 데이터셋)
• 비즈니스 규칙 (결재선, 승인 권한)
• 도메인 특화 ABAC
원칙: 거친 권한은 중앙화돼야 정합성이 유지되고, 세부 권한은 포털 도메인에 묶여 있어 중앙에서 알 수 없습니다.

IDS 권한 모델
회사 출입증과 같습니다
앞 슬라이드의 5개 테이블은 매일 쓰는 회사 출입증 시스템과 같은 구조입니다.
테이블저장 내용회사 비유
User시스템 사용자 명단직원 명부 (이름·사번)
Role정의된 직책·역할"팀장", "일반사원" 목록
Permission제공 가능한 권한 항목"회의실", "서버실" 출입
User_Role누가 어떤 직책인가"홍길동 = 팀장" 출입증
Role_Permission직책별 가능 권한"팀장 → 회의실+서버실" 규정
왜 사람-역할-권한 3단계로 나누나?
❌ 사람한테 권한을 직접 부여하면
홍길동 → [CMP읽기, CMP쓰기, DataHub, AI, ...]
김철수 → [CMP읽기, CMP쓰기, DataHub, AI, ...]
이영희 → [CMP읽기, CMP쓰기, DataHub, AI, ...]
→ 권한 1개 바뀌면 1,000명 다 수정
✅ 역할을 거치면
홍길동 ─┐
김철수 ─┼─→ [팀장] ─→ [CMP, DataHub, AI ...]
이영희 ─┘
→ "팀장" 권한만 한 번 바꾸면 모두 적용
실제 권한 확인 흐름 (예시)
Q. "홍길동이 CMP 데이터를 읽을 수 있나?"

① User에서 홍길동 찾기 → user_id = 42
② User_Role에서 42의 역할 → [팀장, 데이터분석가]
③ Role_Permission에서 권한 합치기 → [cmp.read, cmp.write, ...]
④ cmp.read 있음 → ✅ 허용
핵심: 사람과 권한 사이에 "역할"을 끼워 넣어 관리 부담을 1/N로 줄이는 구조입니다.
부록 ④ 쉬운 설명
각 포털이
책임지는 영역
IDS가 모를 수밖에 없는 "안쪽 세계" — 데이터·업무규칙·도메인 지식이 필요한 권한들.
① 리소스 단위 ACL — "이 자료, 누가 볼 수 있어?"
자료마다 직접 붙은 "출입 가능 명단".

예시
• "2024 수질 데이터셋" → 디지털혁신실 전원 읽기 / 박OO만 수정
• "AI개발용 GPU 워크로드" → AI팀 사용 / 인프라팀 관리

왜 포털이? 데이터셋·워크로드 ID는 매일 생기고 사라짐. 그 자료를 가진 포털만 알 수 있음.
② 비즈니스 규칙 — "결재선·승인 조건"
조직의 업무 흐름에 따른 규칙.

예시
• GPU 4장 이하 → 팀장 결재 / 16장 초과 → 본부장 결재
• 데이터 외부 공개 → 정보공개위원회 결재 필요

왜 포털이? 결재선 바뀔 때마다 IDS 코드 수정하면 모든 포털이 영향받음. 도메인 규칙은 도메인 안에서.
③ 도메인 특화 ABAC — "상황·속성 조합"
사용자·자료·상황 속성을 조합한 동적 판단.

예시
• 본인이 만든 데이터셋만 수정 가능
• 같은 부서 자료만 조회 가능
• 근무시간(09–18) 외엔 운영 변경 불가

왜 포털이? 판단에 필요한 데이터(소유자·부서·프로젝트)가 포털 DB 안에 있음.
방식판단 로직관리 위치
RBAC "팀장이면 → 허용"
역할 한 줄로 결정		 IDS
ABAC "팀장 + 본인 프로젝트 + 근무시간 → 허용"
여러 조건 조합		 각 포털
🎯 한 줄 정리
IDS는 "이 사람이 어느 무대까지 들어올 수 있나"를 결정하고,
각 포털은 무대 안에서 "이 자료를 만질 수 있나"를 결정합니다.
